## 1. 이미 확인된 사실 — 재조사 금지

### 1-1. 깨진 것과 그 원인 (2026-09-29~30 Claude Code가 직접 확인)

  `get_shorting_balance_by_date`(공매도)가 빈 결과 → `KeyError: '거래대금'`.

### 1-2. KRX Open API — 됨 (data-dbg.krx.co.kr)

- 베이스: `http://data-dbg.krx.co.kr/svc/apis`
- 인증: **HTTP 헤더 `AUTH_KEY: <KRX_KEY>`** (쿼리파라미터 아님). `.env`의 `KRX_KEY`.
- 조회 단위: **하루치**(`basDd=YYYYMMDD`). 기간 조회 없음 → 거래일마다 반복 호출.
- 응답: JSON, 배열은 보통 `OutBlock_1` 키. 200 + `Content-Type: application/json`.
- TLS 문제가 나타나면 실제 요청 URL과 인증서 오류를 확인하고 신뢰 저장소를 먼저
  사용한다. `verify=False`를 공통 클라이언트 전체에 기본 적용하지 않는다.

**검증 완료된 엔드포인트** (2026-09-30, basDd=20260929 기준):

### 1-3. 네이버 — 종목 수급은 됨 (API 키 불필요)

- 엔드포인트: `https://m.stock.naver.com/api/stock/402340/trend`
  - 헤더: `User-Agent`(모바일) + `Referer: https://m.stock.naver.com/`
  - 응답 예 한 행:
    ```json
    {"itemCode":"402340","bizdate":"20260929",
     "foreignerPureBuyQuant":"+11,629","foreignerHoldRatio":"46.73%",
     "organPureBuyQuant":"+1,698","individualPureBuyQuant":"-14,216",
     "closePrice":"1,126,000","accumulatedTradingVolume":"434,558"}
    ```
  - 준다: 외국인/기관/개인 **순매수 수량(주)** + **외국인 지분율(%)**.
  - **제약 A — 단위**: 수량(주)이다. 기존 `factor_log.csv`의 `foreign_net`
    /`institution_net`/`individual_net`은 **거래대금(원)**이다(예: 456억). 그냥
    이어붙이면 09-17부터 단위가 바뀌어 시계열이 깨진다.
  - **제약 B — 이력 10일**: 2026-09-30 조회에서 최근 10거래일(20260914~20260929)
    반환; `pageSize` 파라미터로 더 오래된 날짜를 받지 못했다. 응답 원문 10건과
    SHA-256을 `data/snapshots/20260930/naver_trend_402340.json` 및
    `naver_trend_402340_manifest.json`에 보존했다. 09-17~29 누락 거래일 7개는 모두
    포함돼 있다. 이 날짜들의 환산·CSV 반영은 아직 하지 않았다. **이후 날짜도 창에서
    사라지기 전에 원문을 이어서 보존해야 한다.**
  - 보너스: `foreignerHoldRatio` = `factor_log`의 `foreign_own_pct`.
- 네이버 파이낸스 웹(`finance.naver.com/item/frgn.naver`)은 **SPA로 바뀌어 HTML
  스크래핑 불가**(테이블·iframe 없음). 위 JSON API만 유효.
- 네이버 **공매도** API는 못 찾음(후보 404).

### 1-5. NAV·발행주식수 파이프라인 (이미 구현됨, point-in-time)

- `tools/build_listed_holdings.py`: 상장 자회사 일별 지분가치. `build(output, end)`.
  `DEFAULT_END="20260916"`(수기검증 끝단), `--end`로 확장. 보유주식수 구간·소각·
  무상증자 규칙이 `HOLDINGS` dict에 하드코딩.
- `tools/build_nav_daily.py`: 일별 NAV. `build(output, lag, listed_csv)`.
  - 발행주식총수 `SKQ_SHARES`: 자사주 소각일 기준 **계단함수**(DART 교차검증). 현재
    마지막 계단 `("20260731",131_923_998,...)`. 새 소각 있으면 여기 추가.
  - 비상장·순현금 `UNLISTED_EOK`/`NETCASH_EOK`: **분기말 값(Sean 제공)**, 직전분기
    lag 적용. 현재 마지막 `(2026,2)`. 새 분기는 여기 추가.
- `tools/nav_v2.py`: `compute()`(순수 계산, apply_nav_v2와 공유),
  `get_live_nav_v2(date)`(로거 진입점). `_ensure_coverage`가 임시폴더에서 두 CSV를
  만들고 검증 후 **순서대로** `os.replace`한다. 개별 교체는 원자적이지만 두 파일
  전체가 하나의 트랜잭션은 아니다. 두 번째 교체가 실패하면 첫 번째 파일만 갱신될
  수 있으므로, 그 경우 원복하는 절차와 실패 주입 검증이 아직 필요하다.
  `_check_price_freshness`가 재조회 종가와 저장값을 대조(SK스퀘어 포함).
- `tools/factor_logger.py`: `collect_and_log(date)`. NAV는 `get_live_nav_v2`로,
  나머지 팩터는 각 tool로 수집 → 병합 저장(같은 날짜 재저장 시 미수집 항목은
  기존 값 보존, 원자적 쓰기). NAV 실패 시 그 날짜 저장 보류(예외 전파).

## 2. 작업 계획 (1~3번)

> 각 항목은 **사본으로 먼저 검증 → 실제 파일 반영 → 커밋** 순. §6 가드레일 필수.

### STEP 1 — API로 되는 전 구간 일별 데이터 수집

1-A. **선물(F5) 전 구간 백필** — KRX Open API `/drv/eqsfu_stk_bydd_trd`.
   - 상장 이후 SK스퀘어 선물이 상장된 전 거래일에 대해 SK스퀘어 근월물을 골라
     `fut_basis`(선물-현물), `fut_basis_pct`, `fut_volume`, `fut_listed`(상장여부 0/1)
     산출. 미상장 구간은 `fut_listed=0`.
   - 근월물 선택 규칙 정의 필요(최근월 만기물 = 거래량 최대 or 만기 가장 가까운 것).
   - 새 모듈 권장: `tools/krx_openapi.py`(KRX Open API 공통 클라이언트) + 선물 파서.

1-B. **매크로(kospi_ret) 소스 교체 검토** — 현재 비어 있는 `kospi_ret`을 KRX Open API
   `/idx/kospi_dd_trd`로 채울지, 기존 macro.py 경로를 살릴지 결정. `usd_krw`는
   BOK ECOS(✅ 작동) 또는 FinanceDataReader.

1-C. **수급(F3) 최근 갭** — 보존한 2026-09-30 네이버 원문으로 09-17~29 채움.
   단위 통일(§5)에 따라 원 환산 여부 결정. 향후 신규 날짜의 원문도 10일 창에서
   빠지기 전에 보존할 것.

### STEP 2 — 실시간 안 되는 것 백필 (공매도 등)

2-A. **공매도(F4)** — KRX Open API·네이버 모두 없음. 후보:
   - KRX 공매도 종합포털(`short.krx.co.kr`) OTP 스크래핑(GenerateOTP → getJsonData).
     깨지기 쉬움. 되는지 먼저 PoC.
   - 대안 소스(증권사 API, 유료 등) 조사.
   - **과거 공매도는 이미 factor_log(~09-16)에 있음** → 필요한 건 09-17~ 갭 + 향후.
   - 정 안 되면 공매도만 빈 채로 두고 §4 모델을 돌린 뒤 재논의(Sean과 합의).

2-B. **수급 과거 구간** — 이미 factor_log에 있으므로 원칙적으로 백필 불필요. 단
   §5에서 "단위를 수량으로 통일"로 정하면 과거를 못 바꾸므로(네이버 10일 한계)
   → 수량과 원 금액을 같은 열에 혼합하면 안 된다. 신규 구간에 추정 원 금액을 쓰는
   선택지는 있으나 실제 거래대금과 정의가 같지는 않다.

### STEP 3 — NAV·발행주식수 규칙 기반 백필/최신화

3-A. `SKQ_SHARES` 계단에 2026-07-31 이후 신규 자사주 소각 이벤트가 있으면 추가.
3-B. `UNLISTED_EOK`/`NETCASH_EOK`에 2026 Q3 분기말 값 추가(Sean 제공 필요).
   기본 `lag=1` 규칙에서 2026-09-17~29는 **2026 Q2 값을 사용**한다. Q3 값은
   2026 Q4 거래일의 NAV를 계산할 때부터 필요하다. Q3 분기말 값이 확정되기 전의
   Q4 적재는 별도 결측·잠정 정책을 정한 뒤 처리한다.
3-C. `build_listed_holdings`의 `HOLDINGS`에 지분 변동(취득/처분/소각) 반영.
3-D. `DEFAULT_END`를 현재로 확장하거나 `--end` 운용 규칙 문서화.
   → 이 단계는 대부분 **Sean이 값을 제공**해야 하는 부분이 있음. 값 없이 가능한
   부분(파이프라인 확장·계단 함수 로직)만 코드로 처리하고, 값 필요분은 명시.

비어 있다. **감사·검증 도구: `python tools/audit_factor_log.py`**(복구 전후로
재실행해 남은 결측 확인, `--json`으로 기계용 출력). 분류는 (A)최근갭 (B)과거
진짜결측 (C)정상결측(첫거래일·선물미상장·`*_v1` 동결스냅샷 — 복구 대상 아님).
